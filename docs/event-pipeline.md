# Event Detection Pipeline

The event pipeline (v0.2) groups related Discord messages into named, scored "events" — notable server incidents that can be recalled via `/event`. It runs after memory extraction on every message and also runs a nightly maintenance pass.

Source files: `src/event-detection.ts`, `src/event-significance.ts`, `src/events.ts`.

---

## Purpose

Individual memories record facts about people. Events capture *what happened*: the argument, the joke that became a meme, the game night that everyone remembers. An event links:

- A set of **messages** (the raw conversation cluster)
- A set of **memories** (extracted observations from those messages)
- A set of **participants** (who was involved and in what role)
- A **significance score** and **tier** (candidate vs promoted event)
- A **title** and **summary** (generated by the LLM once the event is scored)

---

## Entry points

### `EventPipeline.process(message, savedMemoryIds, eventStore, memoryStore, brain, replyToMessageId?)`

Called from `index.ts` (and `ingest.ts`) after `saveMemory()` on every message where `memoryEnabled` is true. Returns `true` if an LLM call was made (used by `ingest.ts` to pace requests).

### `EventPipeline.maintainEvents(guildId, eventStore, memoryStore, brain, maxAgeMs?)`

Called by the daily maintenance job. Closes stale open windows and scores closed candidate events.

---

## Step 1 — Heuristic scoring

`scoreOpenEvents()` scores all currently open event windows for the incoming channel against a set of cheap signals. **No LLM is called here.**

| Signal | Score contribution |
|--------|--------------------|
| Time recency (linear decay over 4 hours) | 0–0.20 |
| Reply chain (message directly replies to a message in the event) | +0.50 |
| Shared participants (author was already in the event) | +0.20 |
| Keyword overlap with event title+summary | 0–0.20 (0.05 per matching word, capped) |
| Same channel | +0.05 |
| Back-reference phrase ("remember when", "that time", etc.) | +0.10 |

Events older than 4 hours are automatically excluded (score = −1).

---

## Step 2 — Continuity decision

Based on the top heuristic score, one of three paths is taken:

```
top score ≥ 0.60  →  definite ATTACH  (no LLM)
top score < 0.15  →  definite NEW     (no LLM)
0.15 ≤ score < 0.60  →  ambiguous → LLM assessContinuity()
```

The LLM receives up to 3 candidate event windows (each with title/summary and the last 5 messages) and returns one of four decisions:

| Decision | Meaning |
|----------|---------|
| `attach` | Message continues an existing event |
| `new` | Message starts a new conversation thread |
| `reference` | Message mentions a past event but doesn't extend it |
| `bridge` | Message connects two currently open events |

---

## Step 3 — Acting on the decision

### `attach`

The message and its memories are added to the existing event. The author is added to `event_participants` if not already present.

### `new`

A new candidate event window is created **only if the message produced at least one memory**. Ordinary chatter with no memories doesn't get an event window.

### `reference`

The referenced event's `reference_count` is incremented. If `reference_count` reaches 2, `maybeRetroactivelyPromote()` is called — it re-classifies the event cluster and may upgrade its tier from `candidate` to `event`.

### `bridge`

The message is attached to the first (primary) event. The remaining bridged events each receive an incremented `reference_count`.

---

## Daily maintenance — `maintainEvents()`

### Phase 1: Close stale open windows

Any open event window older than `maxAgeMs` (default 24 hours) is closed by setting `closed_at`.

### Phase 2: Score closed candidates

For each closed candidate event that has not yet been scored (`significance = 0`):

1. **Build a cluster** — retrieve the raw messages from the archive (if still present after retention purges) plus participant names and memory count.
2. **LLM classification** — `brain.classifyEvent()` returns `significance` (0–1), `tier` (`low`/`medium`/`high`), `tone`, `narrativeComplete`, `futureRelevant`, `title`, `summary`.
3. **Deterministic scoring** — `calculateSignificance()` combines structural and LLM signals.
4. **Tier assignment** — update the event row.

---

## Significance formula

`calculateSignificance()` in `src/event-significance.ts` is fully deterministic given the LLM's qualitative outputs.

### Inputs

| Input | Source |
|-------|--------|
| `distinctParticipants` | Count of unique participants |
| `messageCount` | Number of messages in the cluster |
| `memoryCount` | Number of memories linked to the event |
| `tone` | LLM: `calm` · `playful` · `argumentative` · `dramatic` |
| `narrativeComplete` | LLM: true if the conversation had a clear beginning and resolution |
| `futureRelevant` | LLM: true if the event is likely to be referenced again |

### Weights

| Signal | Weight |
|--------|--------|
| Distinct participants (0/0.5/1.0 for 1/2/3+) | 0.15 |
| Message count (linear 0–8) | 0.10 |
| Memory count (linear 0–3) | 0.20 |
| Memory count overflow bonus (>3 memories) | 0.10 |
| Tone score (calm=0, playful=0.3, argumentative=0.6, dramatic=1.0) | 0.15 |
| Narrative complete | 0.15 |
| Future relevant | 0.15 |

**Total: 1.00**

### Tier thresholds

| Score | Tier |
|-------|------|
| < 0.35 | discard (kept in DB, never surfaced) |
| 0.35–0.60 | candidate (re-evaluated on next run) |
| ≥ 0.60 | **event** (surfaced via `/event`) |

---

## Retroactive promotion

When a closed candidate event accumulates `reference_count ≥ 2`, it is re-classified immediately (outside of the nightly maintenance cycle). This handles the case where an event was initially too small to score highly but later became clearly significant because everyone kept referring back to it.

---

## Constants (tunable in `event-detection.ts`)

| Constant | Default | Meaning |
|----------|---------|---------|
| `OPEN_EVENT_MAX_AGE_MS` | 4 hours | Events older than this are excluded from heuristic scoring |
| `HEURISTIC_ATTACH_THRESHOLD` | 0.60 | Above this, attach without LLM |
| `HEURISTIC_DISCARD_THRESHOLD` | 0.15 | Below this, treat as new without LLM |
| `MAX_LLM_CANDIDATES` | 3 | Maximum open events sent to the LLM |
| `LLM_CONTEXT_MESSAGES` | 5 | Recent messages per candidate sent to the LLM |
